# Блок 2: AI Prompting & Review — QA-ревью LLM-результата

---

## 1. Общая оценка результата

Сгенерированный LLM-ответ представляет собой **структурированный, но поверхностный тестовый чек-лист**.

Он подходит как:
- черновик тест-дизайна
- генератор идей для сценариев

Но НЕ подходит как:
- финальный QA-артефакт
- основа для тест-менеджмент системы без переработки

---

## 2. Ключевая проблема результата

Основной дефект генерации:

> LLM оптимизирует “широту покрытия”, а не “проверяемость и глубину”

Это приводит к:

- размытым формулировкам
- отсутствию тестовой атомарности
- слабой доменной модели

---

## 3. Сильные стороны

### 3.1 Покрытие основных слоёв системы

Присутствует базовая декомпозиция:

- UI сценарии
- бизнес-логика
- негативные сценарии
- граничные значения
- API поведение

Это говорит о хорошем “macro understanding” системы

---

### 3.2 Базовое понимание API нестабильности

Учитываются:

- timeout
- 500 ошибки
- некорректный JSON
- отсутствие ответа

Это выше среднего для LLM-генерации без явного API контракта

---

### 3.3 Базовая бизнес-логика

Корректно отражены:

- обязательные поля
- ограничения веса/объёма
- дата не в прошлом
- проверка маршрута

минимально достаточный domain skeleton

---

## 4. Критические проблемы

---

### 4.1 Отсутствие тест-кейсов как атомарных сущностей

Главный инженерный дефект.

Сейчас всё представлено как:

- “проверить X”
- “должно работать Y”

Нет:

- шагов (steps)
- ожидаемых результатов (expected result)
- тестовых данных
- предусловий

результат нельзя исполнять или отдавать в команду

---

### 4.2 Слабая доменная модель логистики

Система воспринимается как “форма”, а не как логистический продукт.

Отсутствует:

- тарифная модель
- зоны доставки
- ограничения перевозчиков
- различие бизнес-состояний:
  - нет маршрута
  - нет тарифа
  - маршрут недоступен

это критично для реального продукта

---

### 4.3 API тестирование без контракта

Фактически отсутствует contract testing.

Не проверено:

- структура response schema
- типы полей
- обязательные поля ответа
- бизнес-коды ошибок (не HTTP)
- идемпотентность
- частичные ошибки

API уровень остаётся “UI wrapper testing”

---

### 4.4 UX проверки невалидны как тесты

Формулировки:

- “понятная ошибка”
- “UI не падает”
- “можно повторить запрос”

Проблема:

> нет критериев pass/fail

это не тесты, а ожидания

---

### 4.5 Отсутствуют целые классы рисков

Критически не покрыто:

- security:
  - XSS
  - injection
- concurrency:
  - race conditions при сабмите
- performance:
  - latency degradation
- abuse:
  - spam / rate limit bypass

---

### 4.6 LLM noise (избыточность)

Присутствует:

- повторение базовых сценариев
- очевидные проверки без ценности
- дубли UX кейсов

снижает signal-to-noise ratio тестов

---

## 5. Severity анализ проблем

### HIGH
- отсутствие тест-кейсов (steps + expected)
- отсутствие API contract testing
- неправильная доменная модель

### MEDIUM
- UX неконкретность
- избыточные сценарии
- слабая структура негативных тестов

### LOW
- повторяющиеся позитивные кейсы
- формальные описания без новой логики

---

## 6. Итоговый вывод

LLM-результат:

- полезен как генератор идей
- пригоден как черновик тест-дизайна
- НЕ пригоден как финальный QA артефакт

---

## 7. Ключевой инсайт QA-инженера

> LLM генерирует “покрытие”, но не “проверяемость”

Роль QA-инженера в данном процессе:

- превращать идеи в тест-кейсы
- добавлять доменную строгость
- убирать шум
- вводить критерии проверки
