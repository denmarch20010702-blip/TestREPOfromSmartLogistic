# Блок 2: Проектирование тестов с использованием LLM (AI Prompting & Review)

## Цель задания

Цель данного блока — продемонстрировать умение:
- формулировать качественные промпты для LLM с позиции QA инженера
- получать структурированные тестовые артефакты
- критически анализировать результаты генерации
- выявлять пробелы, ошибки и избыточные проверки
- улучшать тест-дизайн, а не просто использовать AI как генератор текста

---

# Используемая модель

- LLM: ChatGPT (GPT-4o)
- Режим: zero-shot prompting с усиленным контекстом и ограничениями

# 3. Review результата (критический анализ)

## 3.1 Общая оценка

Ответ модели структурирован и покрывает основные сценарии тестирования:
- позитивные сценарии
- негативные сценарии
- граничные значения
- UX проверки
- API интеграции
- бизнес-ограничения

Однако значительная часть проверок остаётся на уровне общих формулировок и требует доработки для использования в реальном QA процессе.

---

## 3.2 Сильные стороны результата

### Структура тестирования
Модель корректно разделяет тесты по типам, что облегчает навигацию и использование результата как чек-листа.

### Базовое покрытие API
Учитываются:
- таймауты
- ошибки 500
- некорректный JSON
- деградация сервиса
- защита от повторных запросов

### Частичная бизнес-логика
Присутствуют ключевые ограничения:
- обязательные поля
- существование маршрута
- логика "город отправления ≠ назначения"
- ограничения веса и объёма

---

## 3.3 Критические недостатки

### Недостаточная доменная глубина (логистика)

Модель не учитывает реальные логистические ограничения:
- тарифные зоны
- географические ограничения маршрутов
- различие между "нет маршрута" и "нет тарифа"
- бизнес-правила перевозчиков

---

### Поверхностное API тестирование

Отсутствует:
- контрактное тестирование (schema validation)
- проверка структуры response
- проверка типов данных
- обработка частичных отказов
- идемпотентность запросов

---

### Неформализованные UX проверки

Большинство UX-проверок:
- не имеют критериев приемки
- не являются проверяемыми
- описаны как ожидания, а не тест-кейсы

Пример проблемы:
- "ошибка отображается понятно" — не измеримо и не проверяемо

---

### Пропущенные классы тестирования

Отсутствуют:
- security testing (XSS, injection)
- performance testing (нагрузка, latency)
- race conditions при изменении формы во время запроса
- abuse сценарии (спам, throttling)

---

### Избыточные проверки

Присутствуют:
- повторяющиеся сценарии успешного расчёта
- общие UX утверждения без добавленной ценности
- очевидные проверки без бизнес-логики

---

## 3.4 Основные выводы

Ответ LLM можно классифицировать как:

- хороший черновик тест-кейсов
- структурированный базовый чек-лист
- не готовый QA-артефакт уровня production

---

## 3.5 Рекомендации по улучшению

Для повышения качества генерации необходимо:

1. Усилить доменную модель (логистика, тарифы, маршруты)
2. Ввести формализацию тест-кейсов (steps + expected result)
3. Добавить контрактное API тестирование
4. Исключить нефункциональные абстракции
5. Явно разделять бизнес-логику и UI проверки

## 4.1 Почему эти границы критичны

- Вес и объём напрямую влияют на стоимость перевозки
- Ошибки приводят к некорректному расчёту тарифа
- Дата погрузки влияет на доступность маршрутов и SLA

# 5. Общий итог

Использование LLM в тест-дизайне показало:

## Плюсы:
- ускорение генерации тестовых идей
- хорошая структуризация сценариев
- покрытие базовых проверок

## Минусы:
- отсутствие глубины доменной логики
- генерация абстрактных UX формулировок
- слабое контрактное мышление
- избыточность простых сценариев

---

## Финальный вывод

LLM эффективно используется как инструмент для первичной генерации тест-кейсов, однако требует обязательного QA review и доработки перед использованием в реальном проекте.

Основная ценность QA-инженера в данном процессе — не генерация, а фильтрация, уточнение и приведение к проверяемому виду.
