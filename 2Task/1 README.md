# Блок 2: Проектирование тестов с использованием LLM (AI Prompting & Review)

---

## 1. Цель задания

Цель данного блока — продемонстрировать навыки QA-инженера в работе с LLM:

- формирование качественных промптов с учётом тестируемости результата
- получение структурированных тестовых артефактов
- критический анализ LLM-выдачи
- выявление логических, доменных и структурных дефектов
- фильтрация избыточных и нетестируемых сценариев
- использование AI как инструмента генерации, а не замены QA-инженера

---

## 2. Используемая модель

- LLM: ChatGPT (GPT-4o)
- Режим: zero-shot prompting с расширенным контекстом и ограничениями
- Роль: симуляция Senior QA Engineer в логистической системе

---

## 3. Методология оценки LLM-результата

Для анализа ответа использовалась следующая модель оценки качества:

### 3.1 Критерии качества

- **Completeness (полнота покрытия)** — покрыты ли основные классы тестирования
- **Testability (проверяемость)** — можно ли однозначно проверить ожидаемый результат
- **Domain correctness (доменная корректность)** — соответствует ли логике логистической системы
- **Noise level (уровень шума)** — наличие избыточных или очевидных проверок
- **Specification alignment (соответствие требованиям)** — учитываются ли ограничения полей и API

## 6. 3. Review результата (критический анализ)

---

## 6.1 Общая оценка результата

Ответ LLM представляет собой:

- структурированный чек-лист тестирования
- частично покрывающий основные сценарии
- содержащий базовую бизнес-логику и API проверки

Однако результат требует существенной доработки для использования в production QA процессе.

---

## 6.2 Сильные стороны результата

### 6.2.1 Структурированность

Ответ разделён на логические блоки:
- позитивные сценарии
- негативные сценарии
- boundary values
- UX проверки
- API интеграции
- бизнес-ограничения

Это упрощает дальнейшую декомпозицию тестов.

---

### 6.2.2 Базовое покрытие API

Присутствуют ключевые сценарии:

- timeout handling
- server errors (500)
- invalid JSON responses
- retry mechanisms
- partial service degradation

---

### 6.2.3 Базовая бизнес-логика

Учтены основные правила:

- обязательность полей
- проверка маршрута
- ограничение веса и объёма
- проверка различия городов

---

## 6.3 Критические недостатки

---

### 6.3.1 Недостаточная доменная глубина (логистика)

Отсутствует учёт реальной логистической модели:

- тарифные зоны и зоны покрытия
- различие между “нет маршрута” и “нет тарифа”
- ограничения перевозчиков
- зависимость стоимости от логистических правил, а не только маршрута

---

### 6.3.2 Поверхностное API тестирование

Не покрыты критические аспекты API-контракта:

- schema validation (контракт ответа)
- проверка типов данных response
- обязательность и структура полей
- частичные ошибки (partial failures)
- idempotency и повторные запросы с одинаковыми параметрами

---

### 6.3.3 UX проверки без критериев измеримости

Большая часть UX проверок не является тестируемой.

#### Пример проблемы:
- “ошибка отображается понятно”

#### Проблема:
нет критериев проверки

#### Улучшенный вариант:
- отображается error code
- указано поле с ошибкой
- текст ошибки соответствует словарю сообщений
- отсутствуют технические детали API

---

### 6.3.4 Отсутствие дополнительных классов тестирования

Не покрыты:

- security testing (XSS, injection)
- performance testing (latency, load)
- concurrency issues (параллельные изменения формы)
- abuse scenarios (spam, rate limiting bypass)

---

### 6.3.5 Избыточные сценарии

Присутствуют:

- повторяющиеся позитивные сценарии без добавления покрытия
- дублирующие UX проверки
- общие утверждения без тестовой ценности

---

## 6.4 Примеры улучшения формулировок

### UX проверка

**Плохо:**
- ошибка отображается понятно

**Хорошо:**
- отображается структурированное сообщение: код ошибки, описание причины, рекомендуемое действие

---

### API ошибка

**Плохо:**
- API возвращает ошибку

**Хорошо:**
- API возвращает HTTP 500 с корректным error schema, включая code, message, traceId

---

## 6.5 Итог анализа LLM

Результат можно классифицировать как:

- структурированный черновик тест-кейсов
- частично корректный чек-лист
- неготовый QA-артефакт production уровня

## 7. 4. Boundary Values Analysis

Граничные значения выделены отдельно для ключевых бизнес-полей:

См. файл: `boundary-values.md`

---

## 7.1 Критичность границ

- Вес и объём напрямую влияют на стоимость перевозки
- Ошибки приводят к некорректному расчёту тарифа
- Дата погрузки влияет на доступность маршрута и SLA
- Нарушение границ приводит к ошибкам бизнес-расчётов

---

## 8. 5. Основные риски использования LLM в QA

- генерация нефункциональных UX формулировок
- отсутствие строгой доменной модели
- смешивание UI и бизнес-логики
- отсутствие контрактного мышления
- избыточность простых сценариев

---

## 9. 6. Общий вывод

LLM эффективно применяется как инструмент генерации первичных тест-идей.

Однако результат требует обязательного QA-ревью, поскольку:

- не гарантирует доменную точность
- не формирует тест-кейсы в проверяемом виде
- склонен к генерации общих формулировок

---

## Финальный вывод

Ключевая роль QA-инженера в AI-подходе:

> не генерация тестов, а их структурирование, валидация и приведение к проверяемому виду с учётом бизнес-домена и системных ограничений.
