# Блок 4: API /api/v2/orders (Test Checklist)

---

## Контекст

Контроллер `/api/v2/orders` реализует REST API для управления жизненным циклом заказа.

API соответствует индустриальным стандартам:

- Google REST API Design Guide
- Microsoft REST API Guidelines

Контроллер поддерживает CRUD операции, логическое удаление и проверку существования ресурса.

---

## 1. Общая стратегия тестирования

Тестирование API выполняется по следующим направлениям:

- корректность HTTP методов (REST semantics)
- проверка статус-кодов
- валидация бизнес-логики
- проверка жизненного цикла сущности
- проверка API контракта (schema validation)
- обработка ошибок и исключений
- проверка авторизации и прав доступа
- работа с несуществующими и удалёнными ресурсами
- обработка системных сбоев
- идемпотентность и конкурентные сценарии

---

## 2. API Contract (модель данных)

### Order Schema (условно)

- id: UUID
- status: string (enum)
- createdAt: datetime
- updatedAt: datetime
- isDeleted: boolean
- customerId: UUID
- items: array
- totalPrice: decimal

---

## 3. GET /api/v2/orders (List Orders)

### Ожидаемое поведение

Возвращает список заказов.

### Проверки

- 200 OK при успешном запросе
- возврат пустого массива [], если данных нет
- возврат только активных (isDeleted = false)
- корректность структуры элементов массива (schema validation)
- проверка типов полей каждого элемента
- проверка обязательных полей ответа
- проверка пагинации (если реализована)
- проверка фильтрации (если реализована)

---

## 4. GET /api/v2/orders/{id}

### Ожидаемое поведение

Возвращает заказ по UUID.

### Статусы

- 200 OK — заказ найден
- 404 Not Found — заказ не существует
- 410 Gone — заказ был логически удалён
- 400 Bad Request — невалидный UUID

### Проверки

- корректный UUID → успешное получение
- невалидный UUID → ошибка валидации
- удалённый заказ → 410 Gone
- проверка schema validation response
- проверка отсутствующих/null полей
- проверка типов данных ответа

---

## 5. POST /api/v2/orders

### Ожидаемое поведение

Создание нового заказа.

### Статусы

- 201 Created — успешное создание ресурса
- 200 OK — если возвращается объект без Location
- 400 Bad Request — невалидный payload
- 409 Conflict — при конфликте идентификатора

### Проверки

- создание с валидным payload
- отсутствие обязательных полей → 400 Bad Request
- дублирование id → 409 Conflict
- проверка генерации UUID (если применяется)
- проверка response schema
- проверка response headers (Location, Content-Type)

---

## 6. PUT /api/v2/orders/{id}

### Ожидаемое поведение

Обновление или создание ресурса (upsert).

### Статусы

- 200 OK — обновление существующего ресурса
- 204 No Content — обновление без тела ответа
- 201 Created — создание нового ресурса через PUT
- 400 Bad Request — невалидный payload

### Проверки

- обновление существующего заказа
- upsert сценарий (создание через PUT)
- обновление несуществующего UUID
- полное и частичное обновление данных
- валидация входных данных
- проверка идемпотентности PUT запросов
- конкурентные PUT запросы (race condition)

---

## 7. DELETE /api/v2/orders/{id}

### Ожидаемое поведение

Логическое удаление заказа.

### Статусы

- 204 No Content — успешное удаление
- 404 Not Found — заказ не найден
- 410 Gone — заказ уже удалён

### Проверки

- удаление существующего заказа
- повторное удаление одного и того же ресурса
- проверка недоступности после удаления
- GET после DELETE → 410 Gone
- идемпотентность DELETE операции

---

## 8. HEAD /api/v2/orders/{id}

### Ожидаемое поведение

Проверка существования ресурса без возврата тела ответа.

### Статусы

- 204 No Content — ресурс существует
- 404 Not Found — ресурс отсутствует
- 410 Gone — ресурс удалён

### Проверки

- корректная проверка существования
- отсутствие response body
- проверка cache behavior (если применимо)
- корректность для удалённых ресурсов

---

## 9. Авторизация и контроль доступа

### Проверки

- 401 Unauthorized — отсутствие или невалидный токен
- 403 Forbidden — недостаточно прав для операции
- проверка доступа к GET / POST / PUT / DELETE / HEAD
- проверка role-based access control (RBAC)
- проверка scope-based access (если применяется)
- запрет доступа к удалённым ресурсам при отсутствии прав

---

## 10. Общие негативные сценарии

- невалидный UUID в path
- отсутствие обязательных полей в POST/PUT
- некорректные типы данных
- пустой request body
- обращение к несуществующему ресурсу
- повторные DELETE запросы
- конкурентные обновления одного ресурса
- malformed JSON payload

---

## 11. Системные сбои и устойчивость

- 500 Internal Server Error (ошибка БД)
- timeout при обращении к сервису
- частичный отказ зависимых сервисов
- некорректный JSON response от backend
- потеря соединения при выполнении запроса
- retry сценарии после сбоя
- деградация сервиса (graceful failure)

---

## 12. Проверки согласованности API

- корректность использования HTTP методов
- соответствие REST принципам (statelessness, idempotency)
- консистентность статус-кодов
- отсутствие утечек внутренней логики в error messages
- единообразие структуры ответов
- соответствие API contract (schema compliance)
